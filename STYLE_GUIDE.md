# Руководство по стилю кодирования команды (Python Style Guide)

Настоящее руководство определяет единые стандарты написания, проверки и сопровождения кода на языке Python (версии 3.10+) в рамках проектной бригады. Базовой основой выступает стандарт **PEP 8**, дополненный обязательными правилами по четырём ключевым направлениям.

---

## 1. Использование комментариев для пояснения сложных участков кода

Код должен быть максимально самодокументируемым за счёт понятных имён, однако комментарии обязательны там, где логика неочевидна из самого синтаксиса.

### Основные правила:
1. **Объясняйте «почему», а не «что».** Комментарий не должен пересказывать синтаксис следующей строки. Он должен фиксировать бизнес-ограничения, математические допущения, обходы багов или причины выбора конкретного алгоритма.
2. **Документируйте публичные интерфейсы (PEP 257).** Каждый публичный модуль, класс и функция должны иметь `docstring` с описанием назначения, аргументов, возвращаемого значения и выбрасываемых исключений.
3. **Не оставляйте закомментированный код.** Устаревшие фрагменты удаляются — история хранится в Git.
4. **Формат рабочих меток.** Допустимы метки `TODO:` и `FIXME:` только с указанием причины и ответственного/задачи.

**Плохо:**
```python
# Увеличиваем счётчик на 1
counter += 1
```

**Хорошо:**
```python
# Сдвигаем окно на 1 элемент вперёд, чтобы исключить повторный учёт граничного замера
window_start += 1
```

## 2. Проверка типов данных и корректности ввода данных

Ошибки некорректных входных данных должны обнаруживаться как можно раньше (принцип *Fail-Fast*) на входе в публичные функции и методы.

### Основные правила:
1. **Обязательная аннотация типов (PEP 484).** Все аргументы и возвращаемые значения функций и методов должны иметь type hints (`int`, `float`, `list[float]`, `dict[str, Any]` и т. д.).
2. **Явная проверка границ и типов.** Для критичных и публичных точек входа проверяйте не только тип (`TypeError`), но и допустимость значений (`ValueError`): пустые коллекции, отрицательные значения там, где они недопустимы, `NaN` и `Inf` для `float`.
3. **Учитывайте ловушку `bool` в Python.** Поскольку `bool` является подклассом `int`, `isinstance(True, int)` возвращает `True`. При проверке числовых аргументов явно исключайте `bool`.
4. **Не подавляйте ошибки молча.** Не возвращайте `None` или пустой результат при невалидном вводе — выбрасывайте информативное исключение с понятным сообщением.

**Плохо:**
```python
def calc_avg(nums):
    return sum(nums) / len(nums)  # Упадёт с ZeroDivisionError или примет [True, False]
```

**Хорошо:**
```python
def calc_avg(nums: list[float]) -> float:
    if not isinstance(nums, list) or not nums:
        raise ValueError("Ожидается непустой список чисел.")
    for idx, val in enumerate(nums):
        if isinstance(val, bool) or not isinstance(val, (int, float)) or math.isnan(val):
            raise TypeError(f"Элемент с индексом {idx} должен быть конечным числом.")
    return sum(nums) / len(nums)
```

## 3. Работа с параллельными процессами и многопоточностью

Многопоточный и многопроцессный код подвержен трудноуловимым ошибкам (состояния гонки, взаимные блокировки, утечки ресурсов).

### Основные правила:
1. **Используйте высокоуровневые пулы и контекстные менеджеры.** Предпочитайте `concurrent.futures.ThreadPoolExecutor` / `ProcessPoolExecutor` внутри блока `with`, чтобы гарантировать корректное завершение потоков/процессов.
2. **Защищайте разделяемое состояние.** Любая запись в общие структуры данных (списки, словари, счётчики) из нескольких потоков должна быть защищена `threading.Lock` (через `with lock:`) либо заменена потокобезопасной очередью `queue.Queue`.
3. **Задавайте таймауты и обрабатывайте исключения задач.** При получении результатов из `Future` используйте таймауты (`timeout=...`) и перехватывайте исключения на уровне конкретной задачи, чтобы сбой одного элемента не обрушил весь пул без диагностики.
4. **Ограничивайте количество воркеров.** Параметр `max_workers` должен быть валидирован (`>= 1`) и ограничен разумным пределом.

**Плохо:**
```python
results = []
def worker(x):
    results.append(x * 2)  # Гонка данных и отсутствие обработки ошибок
```

**Хорошо:**
```python
lock = threading.Lock()
results: list[int] = []

def worker(x: int) -> None:
    computed = x * 2
    with lock:
        results.append(computed)
```

## 4. Рефакторинг кода для улучшения его читаемости, эффективности и поддерживаемости

Код пишется один раз, а читается и модифицируется десятки раз. При обнаружении признаков «запаха кода» (code smells) разработчик обязан провести локальный рефакторинг.

### Основные правила:
1. **Декомпозиция функций.** Если функция превышает ~35–40 строк или решает более одной логической задачи (валидация + вычисления + агрегация + форматирование отчёта), её следует разбить на небольшие, чётко именованные вспомогательные функции.
2. **Уменьшение вложенности (Guard Clauses).** Используйте ранний возврат (`return` / `raise`) для граничных случаев, избегая вложенности `if/for/try` глубже 3 уровней.
3. **Устранение магических чисел.** Все пороговые значения, коэффициенты, таймауты и лимиты выносятся в именованные константы (`UPPER_SNAKE_CASE`) на уровне модуля или параметров конфигурации.
4. **Принцип DRY (Don't Repeat Yourself).** Повторяющиеся блоки логики выносятся в общую функцию или метод с параметризацией различий.
